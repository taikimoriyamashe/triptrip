# EXTRACT_NOTES — latest.json 各フィールドの出所と注意点

対象: `zensha/extract.py` / `zensha/ingest.py`（生成物 `zensha/data/latest.json`）
契約: `zensha/CONTRACT.md` **v1.4** 準拠
基準: 2026-09-18 JST 時点の `zensha/raw/*.md`（ブロック番号は**参考**。実装は全て見出し文字列で特定している）

---

## 0. 全体の方針

- **ブロック番号は一切ハードコードしていない。** 表の特定は必ず「見出しセルの文字列」で行う。
  ブロック番号が本文に出てくるのは `extract_log`（人が読むための記録）だけ。
- 見出し照合は `norm()` で NFKC 正規化 + 空白除去してから行う。
  そのため `Ａヨミ`≡`Aヨミ`、`COST（広告のみ）`≡`COST(広告のみ)`、`体験レッスン 参加率`≡`体験レッスン参加率` を同一視する。
- 数値は `num()` で正規化。`¥ ￥ , ， 円 件 人 %` を除去し、`▲ △ (…)` を負数、
  `#REF! / #DIV/0! / #N/A / #VALUE! / #NAME? / - / 空` を `None`、`[merged]` を含むセルは値として読まない。
  **% は 0–100 の数値**として保持する（契約どおり）。
- **Markdown の列位置は落とさない**（`blocks_probe.py` と違い、空列を詰めない）。
  ズレ検出・列対応の正しさがこれに依存する。
- 欠損は黙って 0 で埋めない。適用した補正は `revenue_corrections`、突合・判断は `extract_log` に日本語で残す。

## 1. 期間・年度（basis_date / data_through / target_month / fy）

| フィールド | 出所・算出 |
|---|---|
| `basis_date` | `--today` 省略時は JST の今日。 |
| `data_through` | `basis_date` の前日（契約どおり）。 |
| `target_month` | **marke の日次表の日付行**（`2026/9/1` 形式の日付が 15 個以上並ぶ行）で最頻の年月。つまり「シート自身が対象としている月」を正とする。取れなければ `data_through` の月。 |
| `days_in_month` | `target_month` のカレンダー日数。 |
| `elapsed_days` | `data_through` が `target_month` 内なら `data_through.day`。`target_month` より前なら 0（月替わり直後）、後なら `days_in_month`。 |
| `remaining_days` | `days_in_month - elapsed_days`（**カレンダーどおり**。シートの「残日数」欄は使わない。marke は 14、kyoten は 13 と食い違っており、原本注記も「カレンダーどおり」）。 |
| `fy.months` / `fy.label` | `target_month` を含む 4 月開始年度の 12 ヶ月を生成（1〜3 月は前年度扱い）。`FY26` 等。 |
| `actual_until_index` | keiei の **「実績確定月→」** セルの右隣の年月（`2026/8`）→ `fy.months` 内の位置 +1 = **5**。 |

**stale（古い raw）ガード**:
- marke の対象月が `data_through` の月とも `basis_date` の月とも違う → **非0終了**。
- `basis_date` が JST の今日と違う（不変条件8）→ **非0終了**。`--today` を明示しても降格しない。
- 両方とも **`--allow-stale` を付けたときだけ**警告に降格して続行する（`extract_log` にも残る）。
- keiei の `計算日_as_of` を読み、`basis_date` と違えば `extract_log` に注意を残す（追加の鮮度チェック）。

## 2. revenue（売上マトリクス）

**表の特定**: `財務会計売上` と `管理会計売上` と `_LKS` `_グロスタ` `合計` を含み、
かつ **`YYYY-MM` が連続 12 列並ぶ月見出し行**を持つブロック（＝ keiei の売上マトリクス、参考: block 2）。

**サブ表の判別**: 月見出し行の**直下の行**が種別行。12 列すべてが同一種別のときだけ確定させる。

| 種別行の値 | 用途 |
|---|---|
| `期初計画` ×12 | `plan` |
| `実績` ×12 | `act` の実績確定月ぶん |
| `Ａヨミ` ×12 | `act` のヨミぶん |
| `実績`×6 + `修正目標`×6（混在） | **スキップ**（この表は `_LKS` 行が空で合計も別定義のため使えない） |

**行の対応**: 月列より左のセルに `財務会計売上`/`管理会計売上` が出たら会計種別を切り替え、
`合計 / _LKS / _MNY / _プロデ / _法人 / _グロスタ`（ワイド表の `_その他` も同義）を系列キーに対応させる。
`計画差` `単月計画差` 等の行は系列ラベルを持たないため自動的に無視される。

### 2-1. act の作り方（CONTRACT v1.3）

- `i < actual_until_index(=5)` → 実績表、`i >= 5` → Ａヨミ表。
- フォールバック順（`extract.py: extract_revenue`）:
  - 実績確定月: **実績 → Ａヨミ → 期初計画 → 0**（確定月で「直前月のヨミ」は使わない）
  - ヨミ月: **Ａヨミ → 直前月Ａヨミ → 実績 → 期初計画 → 0**
  - 適用したら必ず `revenue_corrections` に「どの候補を使ったか」を日本語で記録。
- `total.act` は**シートの合計行ではなく 5 サービスの和**。
  実際、Ａヨミ表の「合計」行は **グロースタジオを含んでいない**（例: fin 2026-04 合計 357,330,856 = LKS+MNY+プロデ+法人）。
  差異が出た月は `revenue_corrections` に記録している。
- `total.plan` はシートの合計行をそのまま（5 サービスの和と一致する）。

### 2-2. Ａヨミ表 `_グロスタ` 行の列ズレ補正（`align_series`）

- シート上のこの行は **先頭に前年度 3 月（2026/3）の値 ¥7,851,000 が入り、以降 1 列右にズレている**。
- 検出は**自動**。実績確定月の実績と突き合わせ、シフト 0〜2 の**一致数が最大（argmax）**のシフトを選び、
  シフト 0 に対して **`max(2, 参照月数の半分)` 以上のマージン**がある場合だけ採用する
  （全件一致を要求しないので、実績が一部欠けていても補正でき、逆に偶然の 1 件一致では誤補正しない）。
  今回は fin/mgmt とも「shift0=0 件 → shift1=5 件 / 参照 5 ヶ月」で 1 列左へ補正。
  マージン未達でシフトを見送ったときは「シフト N を検討したが一致 x/y でマージン未達のため見送り」を `extract_log` に残す。
- **補正の検算（不一致なら非0終了）**: 補正後の `grs.act[当月]` を
  単月確認用（month_summary）の当月 `yomiA` と突合する。
  fin **23,900,300** / mgmt **18,046,000** で一致を確認（`crosscheck_grs_target_month`）。
- **年度末（2027-03）の扱い**: 左シフトで Ａヨミ の 2027-03 が欠落する（13 個ぶんの値が 12 列に貼られ最後が切れている）。
  契約 v1.3 のフォールバック順どおり **直前月Ａヨミ = ¥19,000,000** を採用（fin/mgmt とも）。
  keiei の「実績確定月→ / パターン→Ａヨミ」ワイド表と突合して検算し、`extract_log` に残している:
  `合計 ¥478,789,145 − 他4サービス ¥459,789,144 = ¥19,000,001 / latest.json の fin.grs.act[11] = ¥19,000,000 → 一致`。
  このワイド表はダンプが途中で切れていて mgmt 行が無いため、mgmt は次の「通期Σact 突合」で確認する。

### 2-4. 通期Σact の突合（`crosscheck_fy_landing`）

keiei 単月確認用ブロックの **「[merged] 通期＿全社 → 着地見込み」列**（＝シートの通期着地見込み）と、
latest.json の `Σ revenue[*][*].act` を全 12 系列で突合して `extract_log` に残す。現在:

- **一致 8 系列**: `fin.mny / fin.pro / fin.hjn / fin.grs(¥200,426,630) / mgmt.lks / mgmt.mny / mgmt.pro / mgmt.grs(¥208,485,280)`
  → **mgmt.grs の年度末 ¥19,000,000 フォールバックが 0 円差で裏取りできている。**
- **差あり 4 系列**（ハード失敗にはしない。2-3. の既知の実績改訂で説明できる範囲）:
  `fin.total` / `fin.lks` が +¥1,844,745、`mgmt.total` / `mgmt.hjn` が −¥2,626,479。

### 2-3. 実績の突合（不変条件4）

- `extract.py: check_invariants` が、実績確定月の `act` について
  **「0 以上であること」＋「売上マトリクス実績表の該当セルと一致すること」**を検査する（NG は非0終了）。
  **`¥0` は正当な実績**（例: 財務会計 `_グロスタ` 2026-09 は実績表が ¥0）なので非0終了にせず `extract_log` に記録する。
  非0終了にするのは **負の値**、または **5 サービスすべてが 0 の月**（読み取り失敗の疑い）だけ。
  → 実績確定月が 1 つ進んで 2026-09 が確定月になっても毎朝の実行は止まらない（`test_extract.py: test_regression_cases` の A1 で実証）。
  `total` だけは契約どおり 5 サービスの和なので、シート合計行との差は `extract_log` に参考記録するだけ。
- さらに keiei の **「実績確定月→」実績ワイド表**（`2か月前→` / `FY26通期着地` を持つ表。`_その他`→`grs`）を読み、
  売上マトリクスと食い違うセルを `(会計区分, サービス, 月, 値A, 値B)` の形で `extract_log` に列挙する。
  現在 10 件（`crosscheck_wide_actual`）:

  | セル | 売上マトリクス | ワイド表 |

  | mgmt.total 2026-04 / 06 / 07 / 08 | 380,693,668 / 417,627,105 / 419,878,323 / 437,715,851 | 382,544,011 / 426,736,303 / 430,685,190 / 450,930,125 |
  | mgmt.lks 2026-06 / 07 / 08 | 373,827,873 / 379,019,575 / 395,669,993 | 382,360,935 / 389,826,442 / 408,684,267 |
  | mgmt.hjn 2026-04 / 06 / 08 | 7,464,655 / 3,276,773 / 4,915,286 | 9,314,998 / 3,852,909 / 5,115,286 |

  契約 v1.3 どおり**売上マトリクスを正**としている。ワイド表側は原本(2026-09-08)と同値のまま。
  どちらが正かは経理側の確認が要る（→ 7.）。

## 3. month_summary（単月確認用・検算用）

**表の特定**: `今月→` セルを持ち、`財務会計売上`/`管理会計売上`/`_LKS` を含むブロック（参考: keiei block 3）。

- 見出し行 = `期初計画` `実績` `Aヨミ` `Bヨミ` を全部含む行。
- 列 → 月の対応は、見出し行より上にある **`[merged] YYYY-MM`** 行から取る。
  `target_month` に属する列群だけを使うので、来月・先月の列と混ざらない。
- 値は**シートのまま**格納する（契約 v1.3: 補正しない。表示ではなく検算に使う）。
  契約の例（fin.total: plan 414,385,176 / act 354,487,394 / yomiA 406,123,321 / yomiB 417,009,520）と一致。
- `crosscheck_month_summary` が **yomiA と `revenue[*].act[当月]` の差**を `extract_log` に列挙する（現在 8 件）。
  代表例: `fin.total` 406,123,321 vs 406,430,277（差 306,956）、`mgmt.total` 446,240,375 vs 434,813,265（差 −11,427,110）。
  単月確認用シートは売上マトリクスと別スナップショット／別参照のため差が出る。**表示は revenue 側を使う**。

**注意（シート側のズレ）**: 単月確認用の **管理会計 `_グロスタ` 行は参照がズレている**。
2026-08/2026-09 の期初計画が 27,500,000 / 29,600,000（売上マトリクスでは 24,300,000 / 25,400,000）。
`extract.py` は売上マトリクスの期初計画と突合して**不一致を `extract_log` に残す**が、値は契約どおりシートのまま格納する。
財務会計側はズレていない。

## 5. 実績の数え方が 2 通りある件（原本注記どおり）

- 判定に使う実績 = **KPIサマリ**（`lks.*.act` / `lks.*.yomi`）。
- 日次グラフ = **日次集計**（`lks.*.daily.v`）。
- `extract.py` が両者を突合して `extract_log` に記録する（fail にはしない）:
  - 拠点: 日次合算 **49** ／ KPIサマリ **49** → 一致
  - オンライン: 日次合算 **468** ／ KPIサマリ **477** → 不一致
- 表示側（T2）は「判定＝KPIサマリ / グラフ＝日次集計」で使い分ける。

## 6. sources（raw/<name>.meta.json）

- `ingest.py` は raw を書き出すとき **`raw/<name>.meta.json`**（`title` / `id` / `url` / `ingested_at` / `source_file`）も書く。
  MCP の結果に `title` / `id` が無い場合は `--title` / `--id` で明示でき、それも無ければ CONTRACT 記載の既定値を使う。
- `extract.py` は meta を読んで `sources` を組み立てる。
  - `sources[0]` に `label: "全社（単月確認用・通期着地見通し）"` を付ける（他 2 つは label 無し）。
  - **marke の `name` は `target_month` から組み立てる**（`YY年M月_マーケジスイ進捗管理表`）。
    meta の `title` の年月が `target_month` と違えば `extract_log` に警告（name は target_month 由来の値を使う）。
  - meta が無ければ既定値で埋め、`extract_log` に警告を残す。
    **現在の `zensha/raw/*.md` は ingest.py を経由せず配置されているため、この警告が 3 本出る**（想定どおり）。
  - **marke は ID も月ごとに変わる**。meta から当月の ID を確認できない（meta 無し／title の年月が違う）ときは、
    「『26年10月_…』というラベルで前月分のシートを開くリンクになっている可能性」を marke を名指しで警告し、
    その source に **`stale_id: true`** を立て、`label` に **「（リンク先は前月分の可能性）」** を付ける。
    非0終了はしない（`test_extract.py` の A2 で実証）。

## 9. 月替わり・運用で壊れやすいところ

1. **marke のファイルが月ごとに変わる**（`26年9月_…` → `26年10月_…`）。
   `ingest.py` で `raw/marke.md` と `raw/marke.meta.json` を置き換える運用。
   `target_month` は**シートの日付行**から取るのでファイルが切り替われば自動追従し、
   `sources[1].name` も `target_month` から組み立て直される。ただし:
   - **10/1 の朝**（`data_through` = 9/30）に marke が既に 10 月版だと、`target_month` が 2026-10 になり
     `elapsed_days = 0`（＝日次が空配列）になる。9 月を締めたいなら marke を 9 月版のまま取り込むか、
     `--today 2026-09-30` で回す。
   - marke が**前月版のまま**放置され、`data_through` も `basis_date` も翌月になった時点で**非0終了**する
     （`--allow-stale` を付けたときだけ警告で続行）。
   - meta の title の年月が `target_month` と違うときも `extract_log` に警告が出る（取り込みミスの検知）。
2. **keiei の「今月→」が marke の月とズレると `month_summary` が取れず非0終了**する。
3. **kyoten の `CPA / N月目標 / N月実績` 表の見出しが月名を含む**。当月の表が無い場合は他月の表で代用して
   警告を出す（非0終了はしない）ので、`extract_log` の警告を月初に確認すること。
4. **`実績確定月→` が更新されると `actual_until_index` が動く**（月初に前月が確定して +1 される）。
   act の実績/Ａヨミ境界が変わるので、`revenue_corrections` の内容も変わる。
5. **Ａヨミ表のズレ補正は「実績と突き合わせて検出」する。**
   実績確定月の実績が全部空（年度初め等）だと検出材料が無く、シフトなしで通る（その旨を `extract_log` に残す）。
   補正結果は当月 `yomiA` と突合して守っているが、当月が実績確定月のときはこの検算が効かない。
6. **`_その他` ⇄ `_グロスタ` の表記ゆれ**。売上マトリクスでは `_グロスタ`、ワイド表では `_その他`。
   両方 `grs` にマップしているが、将来 `_その他` が「グロスタ以外の何か」になると誤対応する。
7. **オンライン日次表が複数ある**（marke block 1 と 13）。現在は値が一致するため先頭を採用し、
   不一致なら `extract_log` に警告を残す。
8. **拠点が増減したとき**。`SITES = ["梅田","福岡","横浜"]` / `EXCLUDED_SITES = ["名古屋"]` は
   `extract.py` の定数。日次表の形なのに既知の拠点名が無いブロックがあれば `extract_log` に警告が出るので、
   それを見て定数を直す（契約の `excluded_sites` も連動）。
9. **年度替わり（2027-04）**。`fy_months()` は 4 月開始で自動計算するので `fy.label` は FY27 になる。
   `ORIG_PLAN` は年度ラベルでキーしており FY27 は未登録なので、**不変条件3 はスキップされて警告になるだけ**
   （毎朝の実行は止まらない）。ただしその間は「期初計画が原本どおりか」の守りが無くなるので、
   年度が替わったら FY27 の期初計画を `ORIG_PLAN` に登録すること。
   売上マトリクスの月見出しが FY27 に切り替わっていることも前提。
