# EXTRACT_NOTES — latest.json 各フィールドの出所と注意点

対象: `zensha/extract.py`（生成物 `zensha/data/latest.json`）/ 契約 `zensha/CONTRACT.md`
基準: 2026-09-18 JST 時点の `zensha/raw/*.md`（ブロック番号は**参考**。実装は全て見出し文字列で特定している）

---

## 0. 全体の方針

- **ブロック番号は一切ハードコードしていない。** 表の特定は必ず「見出しセルの文字列」で行う。
  ブロック番号が本文に出てくるのは `extract_log`（人が読むための記録）だけ。
- 見出し照合は `norm()` で NFKC 正規化 + 空白除去してから行う。
  そのため `Ａヨミ`≡`Aヨミ`、`COST（広告のみ）`≡`COST(広告のみ)`、`体験レッスン 参加率`≡`体験レッスン参加率` を同一視する。
- 数値は `num()` で正規化。`¥ ￥ , ， 円 件 人 %` を除去し、`▲ △ (…)` を負数、
  `#REF! / #DIV/0! / #N/A / #VALUE! / #NAME? / - / 空` を `None`、`[merged]` を含むセルは値として読まない。
  **% は 0–100 の数値**として保持する（契約どおり）。
- **Markdown の列位置は落とさない**（`blocks_probe.py` と違い、空列を詰めない）。
  ズレ検出・列対応の正しさがこれに依存する。

## 1. 期間・年度（basis_date / data_through / target_month / fy）

| フィールド | 出所・算出 |
|---|---|
| `basis_date` | `--today` 省略時は JST の今日。 |
| `data_through` | `basis_date` の前日（契約どおり）。 |
| `target_month` | **marke の日次表の日付行**（`2026/9/1` 形式の日付が 15 個以上並ぶ行）で最頻の年月。つまり「シート自身が対象としている月」を正とする。取れなければ `data_through` の月。 |
| `days_in_month` | `target_month` のカレンダー日数。 |
| `elapsed_days` | `data_through` が `target_month` 内なら `data_through.day`。`target_month` より前なら 0（月替わり直後）、後なら `days_in_month`。 |
| `remaining_days` | `days_in_month - elapsed_days`（**カレンダーどおり**。シートの「残日数」欄は使わない。marke は 14、kyoten は 13 と食い違っており、原本注記も「カレンダーどおり」）。 |
| `fy.months` / `fy.label` | `target_month` を含む 4 月開始年度の 12 ヶ月を生成（1〜3 月は前年度扱い）。`FY26` 等。 |
| `actual_until_index` | keiei の **「実績確定月→」** セルの右隣の年月（`2026/8`）→ `fy.months` 内の位置 +1 = **5**。 |

**安全弁**: marke の対象月が `data_through` の月とも `basis_date` の月とも違う場合は
「古い raw を使っている可能性」として**非0終了**する（`--today 2026-10-05` で確認済み）。
さらに keiei の `計算日_as_of` を読み、`basis_date` と違えば `extract_log` に警告を残す（鮮度チェック）。

## 2. revenue（売上マトリクス）

**表の特定**: `財務会計売上` と `管理会計売上` と `_LKS` `_グロスタ` `合計` を含み、
かつ **`YYYY-MM` が連続 12 列並ぶ月見出し行**を持つブロック（＝ keiei の売上マトリクス、参考: block 2）。

**サブ表の判別**: 月見出し行の**直下の行**が種別行。12 列すべてが同一種別のときだけ確定させる。

| 種別行の値 | 用途 |
|---|---|
| `期初計画` ×12 | `plan` |
| `実績` ×12 | `act` の実績確定月ぶん |
| `Ａヨミ` ×12 | `act` のヨミぶん |
| `実績`×6 + `修正目標`×6（混在） | **スキップ**（この表は `_LKS` 行が空で合計も別定義のため使えない） |

**行の対応**: 月列より左のセルに `財務会計売上`/`管理会計売上` が出たら会計種別を切り替え、
`合計 / _LKS / _MNY / _プロデ / _法人 / _グロスタ`（ワイド表の `_その他` も同義）を系列キーに対応させる。
`計画差` `単月計画差` 等の行は系列ラベルを持たないため自動的に無視される。

### 2-1. act の作り方（契約どおり）

- `i < actual_until_index(=5)` → 実績表、`i >= 5` → Ａヨミ表。
- 欠損時のフォールバック順は **Ａヨミ→実績→0**。適用したら必ず `revenue_corrections` に日本語で記録。
- `total.act` は**シートの合計行ではなく 5 サービスの和**。
  実際、Ａヨミ表の「合計」行は **グロースタジオを含んでいない**（例: fin 2026-04 合計 357,330,856 = LKS+MNY+プロデ+法人）。
  差異が出た月は `revenue_corrections` に記録している。
- `total.plan` はシートの合計行をそのまま（5 サービスの和と一致する）。

### 2-2. Ａヨミ表 `_グロスタ` 行の 1 列ズレ補正

- シート上のこの行は **先頭に前年度 3 月（2026/3）の値 ¥7,851,000 が入り、以降 1 列右にズレている**。
- `align_series()` が**自動検出**する: 実績確定月（0..4）の実績と、シフト 0 / 1 で突き合わせて
  「シフト 1 のときだけ全月一致」なら 1 列左に戻す。ズレていない行は動かさない。
  → 番号や行名を決め打ちしないので、他の行がズレても同じ仕組みで直る。
- 結果（受入基準どおり）: `fin.grs.act[5]` = **23,900,300**（7,851,000 ではない）、`mgmt.grs.act[5]` = **18,046,000**。
  どちらも単月確認用シートの当月 Ａヨミ と一致する。
- **見つからなかった値**: 左シフトの結果、**2027-03 の Ａヨミ が欠落する**（13 個ぶんの値が 12 列に貼られ、最後が切れているため。
  「通期合計」列も 12 セルの単純和なので復元に使えない）。
  契約のフォールバック順どおり実績表の値（fin/mgmt とも ¥0）を採用し、`revenue_corrections` に記録している。
  原本は 19,000,000 を持っていた（→ 「6. 契約への提案」参照）。

## 3. month_summary（単月確認用）

**表の特定**: `今月→` セルを持ち、`財務会計売上`/`管理会計売上`/`_LKS` を含むブロック（参考: keiei block 3）。

- 見出し行 = `期初計画` `実績` `Aヨミ` `Bヨミ` を全部含む行。
- 列 → 月の対応は、見出し行より上にある **`[merged] YYYY-MM`** 行から取る。
  `target_month` に属する列群だけを使うので、来月・先月の列と混ざらない。
- 行は revenue と同じ会計種別 × 系列ラベルの対応。
- 値はシートのまま格納する（加工しない）。契約の例（fin.total: plan 414,385,176 / act 354,487,394 /
  yomiA 406,123,321 / yomiB 417,009,520）と一致。

**注意（シート側のズレ）**: 単月確認用の **管理会計 `_グロスタ` 行は参照がズレている**。
2026-08/2026-09 の期初計画が 27,500,000 / 29,600,000（売上マトリクスでは 24,300,000 / 25,400,000 = 2 ヶ月ぶん先の値）。
`extract.py` は売上マトリクスの期初計画と突合して**不一致を `extract_log` に残す**が、値は契約どおりシートのまま格納する。
財務会計側はズレていない。

## 8. 月替わり・運用で壊れやすいところ

1. **marke のファイルが月ごとに変わる**（`26年9月_…` → `26年10月_…`）。
   `ingest.py` で `raw/marke.md` を置き換える運用。`target_month` は**シートの日付行**から取るので
   ファイルが切り替われば自動追従する。ただし:
   - **10/1 の朝**（`data_through` = 9/30）に marke が既に 10 月版だと、`target_month` が 2026-10 になり
     `elapsed_days = 0`（＝日次が空配列）になる。9 月を締めたいなら marke を 9 月版のまま取り込むか、
     `--today 2026-09-30` で回す。
   - marke が**前月版のまま**放置され、`data_through` も `basis_date` も翌月になった時点で**非0終了**する
     （stale raw ガード）。
2. **keiei の「今月→」が marke の月とズレると `month_summary` が取れず非0終了**する。
   keiei シートの今月セルが更新されているかが前提。
3. **kyoten の `CPA / N月目標 / N月実績` 表の見出しが月名を含む**。当月と一致する表だけを採るので、
   シート側が月初に更新されていないと `sites` が取れず非0終了する。
4. **`実績確定月→` が更新されると `actual_until_index` が動く**（月初に前月が確定して +1 される）。
   これが動くと act の実績/Ａヨミ境界が変わるので、`revenue_corrections` の内容も変わる。
5. **Ａヨミ表のズレ補正は「実績と突き合わせて検出」する。**
   実績確定月の実績が全部空（例: 年度初め 4 月で `actual_until_index` が小さい）だと検出材料が無く、
   シフトなしのまま通る。年度替わり直後は `revenue_corrections` を目視確認したい。
6. **`_その他` ⇄ `_グロスタ` の表記ゆれ**。売上マトリクスでは `_グロスタ`、ワイド表では `_その他`。
   両方 `grs` にマップしているが、将来 `_その他` が「グロスタ以外の何か」になると誤対応する。
7. **オンライン日次表が複数ある**（marke block 1 と 13）。現在は値が一致するため先頭を採用し、
   不一致なら `extract_log` に警告を残す。将来片方が別定義になったら見出し条件を足す必要がある。
